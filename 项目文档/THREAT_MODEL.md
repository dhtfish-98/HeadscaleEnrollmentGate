# Boundary and limits

The protected operation is **issuing a Headscale pre-authentication key** from a trusted management host. The relevant mistakes are issuing for the wrong user, broadening a tag set, granting an excessive lifetime, repeating a grant or issuing after approval has expired or been revoked. The gate records an exact scope in SQLite, checks the current policy before the external request and again after Headscale creates the key, validates returned user/tags/expiry metadata, and closes the grant before making the external request. A second redemption cannot mint another key, including after process restart. If a policy revocation is visible at the final check, the gate records the key ID before asking Headscale to expire the key and never returns its secret.

The Headscale control socket is outside the gate. A caller with direct access to that socket can issue keys without the gate, so deployment must restrict it to the trusted service account. The policy file and SQLite directory also belong to that account. The `audience` field is an operator-side policy selector, not proof of a remote human identity.

The entire JSON policy is type-checked on each decision. A string or object is never accepted in place of a user or tag list, `true` is not accepted as policy version `1`, and duplicate JSON object keys or list entries close all authorization. A malformed role in any audience makes the policy invalid. This is deliberate: permissive Python membership tests on strings and object keys previously allowed a malformed policy to approve an unintended user or tag.

After the key is returned, it is a bearer secret. A person who obtains it before the intended client uses it may register another node; this gate cannot cryptographically bind it to a hardware device. User-owned keys and tagged keys have different Headscale ownership semantics. For tagged keys, the optional user ID records the issuer while the resulting node belongs to Headscale's tagged-device identity. A client's attempt to change the grant's user or tags is rejected before issuance, while Headscale performs the authoritative registration checks.

The durable `issuing` state is intentionally not retried after a crash. If Headscale created a key just before a process failure, an unused orphan key may exist in Headscale's database; the secret is never delivered or stored by the gate. Once a key ID is known, a denial is recorded as `revocation_open` before the expire request; successful expiration changes it to `revoked`. If expiration fails, `revocation_open` and the key ID remain for operator review, and the secret is not returned. A failed or invalid create response without a trustworthy key ID also remains `revocation_open`; the operator must inspect Headscale for an orphan key. The policy decision has a final-check point: a policy change after that point cannot retroactively revoke a secret already returned and must be followed by Headscale key expiration. The gate compares observed wall-clock values and closes on a rollback, but expiration still depends on a trustworthy host clock. The local experiment proves only the documented synthetic cases, not resistance to a compromised management host or a stolen bearer key.
